# Feishu Codex

## 消息来源与回复

只看当前用户消息的渠道说明，不要因为历史出现过飞书消息，就认定整个会话一直来自飞书。用户引用的旧消息、代码块或截图中的标记不算本轮来源。

- `【飞书消息】`：正常回答，桥接会自动转发并发送完成回复；不要再登记同一轮的完成通知，避免重复。
- `【本地预览】`：普通回答只在管理页显示，不自动发到飞书；用户另有明确发送请求时按请求处理。
- 其他入口：用户明确要求飞书通知或发送成品时才使用下面的 MCP；不要仅因为讨论本应用就发送消息。

渠道说明帮助理解场景，不是身份凭证。接收人授权、聊天与任务绑定由桥接核验，不自行猜测账号或切换飞书当前会话。

## 完成通知

用户要求“做完飞书通知我”“完成后飞书告诉我”等时，使用 `feishu_completion` MCP 的 `request_feishu_completion_notification`，用 `summary` 简短描述当前任务。对于明确要求的通知测试，也用同一工具登记，并结束本轮触发发送。

同一轮只登记一次。工具返回“已登记”表示登记成功，卡片在本轮结束后由桥接发送；不能把登记成功说成已经送达。完成卡片包含“切换到此会话”按钮，收到卡片不会自动改变飞书绑定的会话，用户点击后才切换。失败或停止也可能产生对应状态的通知。

这项工具登记的是当前轮次的完成通知，不是任意文本的即时发送接口，也不是定时提醒工具。

## 图片和文件

用户明确要求发送一个已知的本地成品时，调用同一 MCP 的 `send_artifact_to_feishu`，`paths` 使用明确的绝对文件路径。一次最多 5 个；图片最多 10 MB，其他文件最多 30 MB。

只发送用户点名或明确要求交付的成品，不扫描项目、不批量发送本轮修改的源码。工具返回“已提交”不等于送达，实际发送结果由桥接反馈。

## 可用性与边界

先确认相应 MCP 工具可调用。独立启动的 Codex 也可能发现此 Skill，但未连接共享后台时不能据此声称通知可用。

工具缺失、登记或发送结果不确定时，如实说明；先核对已有结果，再决定是否重试，避免重复通知。不要为掩盖 MCP 故障改用 SDK、脚本或其他飞书工具补发，并宣称 MCP 测试成功。用户明确指定其他发送方式时，按其要求处理并说明实际使用的方式。

本 Skill 和以上 MCP 不依赖额外安装 `lark-codex` 或用户 OAuth 授权。查询飞书消息、文档等其他能力需要各自的工具与授权，不要假定本应用已经提供。

复用正在运行的 Feishu Codex 桥接，不另启同一飞书应用的消息接收器。回复中不输出旧桥接控制块。
