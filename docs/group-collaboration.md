# 群聊角色协作

在同一个飞书群里添加多个机器人，分别承担产品、开发、测试等角色。每个机器人在这个群里使用独立的会话，可选择 Codex 或 Hermes 执行端；你通过手动 @决定谁执行工作。

## 配置

1. 为每个机器人创建一个独立的飞书自建应用，开启机器人能力、长连接和 `im.message.receive_v1`。卡片交互使用 `card.action.trigger`。基础步骤见 [配置指南](getting-started.md)。同一个 App ID 只能配置一次。
2. 在开放平台为每个应用开通“接收群聊中 @机器人消息”（`im:message.group_at_msg:readonly`）及发送消息权限，并发布版本。
3. 在本应用“机器人”页面添加机器人，选择 Codex 或 Hermes，填写名称、App ID 和 App Secret；验证后自动连接，并进入“访问权限”。在“对话设置”中填写群聊角色说明。Codex 的模型与推理强度留空时沿用本机配置；Hermes 沿用 Hermes 的模型配置，需要本机已安装 Hermes 并配置模型，服务由本应用自动启动。
4. 将机器人添加到同一个飞书群，分别 @它们发一条消息。
5. 在左侧选择对应机器人，在“访问权限”中分别允许自己的账号和这个群，然后重新 @发送消息。群聊授权不会自动授权群成员，一个机器人的授权也不会自动复制给其他机器人。
6. `@机器人 /project` 选择本机项目，随后发送工作要求。第一次工作会创建专属角色会话。

引用平台消息需要具备读取对应消息的权限。希望普通群聊发言也成为背景时，需要额外开通获取群内用户消息的权限；以开放平台 [接收消息](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive) 和 [获取指定消息](https://open.feishu.cn/document/server-docs/im-v1/message/get) 的当前权限要求为准。未开通时仍可使用已接收的 @消息及本应用机器人发布的结果进行协作。

## 如何使用

```text
@产品经理 设计登录流程，列出验收标准
@开发 按上面的方案实现
@测试 根据需求检查开发结果
```

引用具体方案消息再 @目标机器人，交接内容更明确。多个方案有歧义时，机器人应先澄清。

- 没有 @时不主动回答；上一条 @过，也不表示后续消息自动触发。
- 同时 @多个机器人，每个被 @的机器人各自收到一次要求。
- 同时 @多个机器人发送 `/new`、`/status`、`/stop` 或 `/session`，会分别作用于每个已授权且在线的机器人。`/session` 只分别展示各自的会话列表，后续在对应机器人的卡片上选择；各机器人的会话编号不能混用。
- 普通提及只进入公共背景；机器人明确申请交接时，桥接可以安排另一角色继续，规则见下方“机器人交接”。
- 背景只包含该群当前项目的有限近期公开消息和明确引用，不复制其他角色的完整历史、工具日志或私聊。长方案可引用原消息，或使用项目中的文档。
- 同一个本机项目的群聊任务会排队，避免不同角色同时修改文件。当前同一角色会话的补充消息仍可加入正在处理的任务；`/stop` 可以取消等待。

## 项目与会话

一个群共用一个项目。通过任一机器人切换群项目，会为群里各角色准备该项目的新会话；有任务运行时需先等待结束。不同机器人拥有各自的 `/new` 和 `/session`；Codex 的模型与推理强度可分别设置，Hermes 的模型在 Hermes 中设置。

群里的 `/session` 只展示当前机器人在这个群、当前执行端创建或使用过的专属会话。Codex 会话可以在 Codex 桌面打开并继续工作，之后再次 @对应机器人接着处理。Hermes 使用独立会话，不能在 Codex 桌面接续，也不能把 Codex 会话直接切换给 Hermes。机器人创建后不能更换 Codex／Hermes；如需更换，请删除该机器人后重新添加。

选择不同的旧会话后，继续使用该会话的原有历史和角色，同时从切换成功时重新积累自动群聊背景；离开期间的群聊不会自动补入。仅查看会话列表、重复选择当前会话或切换失败都不改变背景起点，其他机器人的会话和背景起点也不受影响。

在“机器人 → 对话设置”中可分别填写群聊和私聊角色说明。群聊沿用已配置的机器人角色；私聊说明默认留空，使用所选执行端的普通会话，不继承群聊角色或机器人名称。需要固定的个人助手职责时，可以选填独立的私聊说明。执行端设置对该机器人的群聊和私聊均生效。

角色说明在创建会话时固定。编辑或清空说明后，请在对应的私聊或群聊中使用 `/new` 新建会话；已有会话保留原角色，Codex 会话在桌面继续也保持一致。升级前已带角色的私聊不会自动清除角色；要使用普通会话，请保持私聊说明为空并新建会话。从 Codex 桌面选择的既有会话也不会被强加新的机器人角色。

升级机器人交接功能时，应用会为自己管理的空闲群会话补充协作说明，保留原角色、会话 ID 和历史。

固定回复规则和 Skill 指引通过独立应用上下文提供；用户消息首行只保留 `【飞书消息】` 或 `【本地预览】`，同时兼容带完整说明的旧版消息头。渠道按当前消息判断，历史、引用和代码中的标记不算本轮来源；桌面续聊没有标记时，不会仅因会话过去来自飞书就自行转发普通回复。

群任务排队只协调本应用提交的群聊任务。直接在桌面操作多个会话时，仍应避免同时修改同一份文件。

## 机器人交接

可以直接安排团队任务，例如：

```text
@产品经理 设计一个待办小工具，然后交给开发人员复述方案；这次只讨论，不修改代码。
```

应用自带的 `feishu-codex` Skill 说明固定协作规则。每条消息只附带当前可用角色；自动交接另外附带来源角色、交接次数和原始任务。Codex 和 Hermes 优先调用 `feishu_completion` MCP 的 `request_feishu_group_handoff`，例如传入：

```json
{"target":"开发人员","task":"复述上面的三个功能，说明实现顺序，不要修改代码。"}
```

`target` 选择本轮可交接名单中的一个其他角色；遇到同名或特殊名称时，使用消息中提供的角色编号。`task` 是用户已授权范围内的具体工作。工具返回成功只表示已提交申请，不表示目标已经收到或开始执行。调用工具后，最终回复正常说明结果，不再附带可执行的文字交接行，避免两路派发。

只有工具不存在时才使用文字兼容方式，在最终回复最后一行单独写：

```text
交接给 @开发人员：复述上面的三个功能，说明实现顺序，不要修改代码。
```

已经调用工具但失败或状态不明时，机器人应告知用户，不能自动改用文字重试、重复调用或另找接口派发。交接仅适用于桥接核验的当前真实飞书群轮，私聊、本地预览和桌面续聊均不提供群路由；历史群绑定或消息中的标记不能代替本轮来源。

桥接会核验双方账号和群授权、同一项目路径、目标会话忙闲状态及交接次数；只有源回复确认送达、源轮结束并释放项目占用后，才把交接任务、原用户要求和公开群聊背景交给目标角色自己的会话。卡片中的普通 `@名称` 不等于派发；代码示例、引用、随口提及、自己 @自己和无法区分的名称不会自动执行。一轮只能指定一个目标。

重复调用或重复事件不会重复派发。文字兼容方式在同一回复重复交给同一个角色时，只采用最后一条明确任务。目标角色已经收到你的消息、正在处理或排队时，不重复派发；排队任务开始时会读取最新群聊背景。同一轮追加要求会使旧交接申请失效，完成回复以最新要求下的最后一版回答为准。

- 两端机器人、操作者和群均须授权并已连接。跨应用账号只按飞书提供的身份信息或同一条真实消息关联，不按姓名或授权名单猜测。首次使用可同时 @两位机器人发送“协作测试”，建立账号关联。
- 一个用户任务最多自动交接 6 次，超过后提示暂停。需要继续时由你手动 @指定角色。
- 你再次 @下达新要求，旧任务不再继续接力；不 @的普通群发言仍只是背景。
- 向参与的任一机器人发送 `/stop`，可停止自己发起的本群接力。进度卡片的停止按钮只作用于它对应的任务，旧卡片不会停止新任务。
- 目标角色正在桌面执行其他任务时，自动交接不会混入该任务，会明确提示稍后手动继续。
- 失败、中断、授权撤销、切换项目/会话、回复送达不确定或服务退出时，不继续自动接力；交接异常会提示原因，不自动重试或重放未确认的指令。

机器人间的消息仍由现有桥接内部传递，无需安装额外飞书 CLI 或新增消息接收服务。交接在源轮结束后执行，同一项目的任务占用规则不会因交接而绕过；需要在本轮取得另一角色的分析意见时，使用下方的同步咨询。

## 通知与审批

工作结果、附件和审批沿用本轮的机器人和群聊。审批只能由原请求账号在原聊天处理，或在本机管理页处理。Codex 桌面继续旧的角色会话，即使飞书已 `/new`，已知来源的完成通知也仍发往原机器人和原群；不会自动切换当前会话。此桌面完成通知能力不表示 Hermes 已接入相同的 MCP。

桌面任务没有明确群绑定时，不自动猜一个群发送。只有唯一已授权私聊时，才沿用私聊通知默认目标。机器人离线时，尚未发送的完成通知保持等待；不会把同一通知广播到所有机器人。

## 本地验收

1. 群内不 @，确认没有机器人回答；分别 @两个机器人，确认身份和会话独立。
2. 产品机器人输出方案，引用它并 @开发，确认开发能识别方案。
3. 对其中一个机器人 `/new`，确认另一个的会话不变。
4. Codex 桌面打开 Codex 角色会话继续一轮，再从飞书接着问，确认历史连续；Hermes 会话不交给 Codex 桌面接续。
5. 同项目同时向不同机器人提要求，确认等待及停止等待有效。
6. 撤销其中一个机器人对群的授权，确认它不能继续执行，其他机器人仍正常。
7. 在群里安排一次明确交接，确认 Codex 和 Hermes 均可使用工具申请；申请时目标尚未执行，源回复送达并结束后才交给目标，且只执行一次。

### Hermes 的 Skill 与 MCP

首次通过桥接使用 Hermes 时，应用会在本机 Hermes 的 Skill 目录安装专用的 `feishu-codex`，并配置群交接与同步咨询 MCP。Hermes 对话服务由应用自动启动，无需打开 Hermes 桌面；首次加载工具时若还有任务运行，请等其结束再试。后续普通消息不会反复重载工具。

固定规则保存在 Skill 中，各会话的角色说明使用独立的版本文件。每轮只带 Skill 和当前角色的简短引用，Hermes 首次使用或上下文缺失时按需读取。已有聊天记录、模型和全局角色不迁移；此前历史中的长消息不会自动删除。

内置 Skill 由应用维护，角色偏好请在机器人的对话设置中填写。升级或重装后，如果带本应用管理标记的 Hermes Skill 被修改，应用会先把原文件和标记备份到当前 Hermes profile 的 `.feishu-codex/skill-backups/`，再恢复安装包内的版本；备份位置会记录到日志。没有本应用管理标记的同名 Skill 不会被接管，个人角色引用也不会被覆盖。

桥接仅核验自己发起的当前群聊轮次。即使 Hermes 关闭工具进度，也可以从当前轮的原生工具记录补验交接；记录缺失、被截断或无法确认归属时，不派发。Hermes 桌面独立发起的任务不在此群交接范围内。此 MCP 尚不提供 Hermes 桌面完成通知或文件发送。
8. 在交接申请后追加要求，确认旧申请失效；私聊、本地预览、桌面续聊以及普通提及均不能触发群交接。
9. 让目标会话忙碌或撤销授权，确认交接停止并提示原因，没有自动重试或改用另一种方式派发。

本功能参考了 [cc-connect](https://github.com/chenhg5/cc-connect) 的精确 @识别、引用消息和群聊公共上下文设计。

## 群聊上下文如何传递

每个机器人保留自己的执行端会话历史。桥接按机器人、群、项目和会话保存已送达记录，同一会话只补充还没收到的公开群消息，不再每轮重复附加整个近期记录。当前用户消息和该会话自己的回复不会作为背景再次发送；用户明确引用的消息会单独附带一次。

群聊背景、明确引用和交接信息仍随当前用户消息传入，不迁入固定应用规则，也不因此获得新的操作授权。送达核验继续使用包含本次群资料和唯一批次的原始输入。

机器人首次参与群聊时，从最近 20 条公开记录中选取背景。主动发送 `@机器人 /new` 或在管理页新建会话时，会同时设置新的群聊背景起点：此前的群记录不再自动带入，只补充起点之后的新讨论。每个机器人独立重置，不删除公共群记录；明确引用或交接仍可携带指定的旧方案。角色和项目设置保持不变。

通过 `/session`、管理页或“切换到此会话”成功选择不同的旧会话时，背景起点同样重置到切换成功时。原会话的执行端历史、角色和会话 ID 保留，但不再自动补入离开期间的群记录；切换之后的新讨论仍正常补充。仅列出会话、重复选择当前会话或切换失败不会重置。此规则同时适用于 Codex 和 Hermes，明确引用和交接仍可携带指定的旧内容。

背景受每次 16000 字符预算限制。长消息分段传递，未送达的部分仍可在后续补充，但不会跨过当前会话的背景起点。桥接本机每群最多保留 100 条记录，群数量和总文本量也有限制，因此这不是完整群聊归档。需要指定旧方案时，请直接引用它。

送达记录在执行端确认接收后才保存。提交失败不会提前跳过背景；接收状态不明时，后续只读核对会话原始输入，确认匹配才记为已送达，不自动重发原用户任务。服务重启继续使用当前保存的背景起点和送达记录，不会重新补入起点之前的讨论。升级时不会主动重置已有会话；之后新建会话或成功切换到不同会话时，按上述规则设置新起点。

Codex 原有上下文管理、压缩和桌面接续保持不变。本机制减少重复注入，不会删除既有会话历史，也不会自动把所有群记录传给每个机器人。

群聊参考资料使用“本机时间 · 发言人”和分行引用展示，不再重复包裹 JSON 字段。未知姓名以稳定的群友简称区分；存储和授权仍使用原账号标识。内部批次缩短显示，送达核验仍沿用原始输入哈希。


## 选择是否补充群聊背景

在“机器人”页面左侧选择机器人，在“对话设置”中设置“补充群聊背景”。每个机器人独立保存，默认开启，修改后自动保存并对后续提交生效。

- 开启：按现有增量机制补充已接收、已授权的同群当前项目讨论。
- 关闭：停止自动补充群记录，保留当前 @该机器人的任务、明确引用和交接内容。该机器人的会话历史继续保留，无需新建会话。
- 同群其他机器人的设置、群消息收集和回复触发规则不受影响；没有 @仍不会主动回复。
- 重新开启沿用原送达记录，只补充本机仍保留且尚未传入的背景，不保证补齐关闭期间的全部消息。

关闭后若要使用另一位机器人的方案，请引用那条方案再 @目标机器人，或明确交接。切换开关不会删除已进入会话的历史。

## 群内同步咨询

可以让当前机器人先听取另一角色的意见，再综合回答：

```text
@开发 请先问测试角色这个登录方案有哪些边界风险，再给我你的结论。这次只分析。
```

Codex 和 Hermes 使用 `feishu_completion` MCP 的 `consult_feishu_group_agent`。参数为 `{context_token, target, question, context?}`：票据 `context_token` 由桥接在当前真实群轮的 `<feishu_group_consultation>` 动态上下文中提供，`target` 是本轮名单中的其他角色名或角色编号，`question` 是分析问题，`context` 可选，仅补充必要且允许共享的当前任务或本群公开资料。票据只用于当前源轮，不能从历史消息、群绑定或示例中复用、猜测。

正常咨询流程依次是：来源机器人公开提问并 @目标机器人，目标机器人公开回答，来源机器人结合答案继续处理。桥接先以来源机器人的身份，在发起咨询的同一个飞书群发布 `question`，并使用飞书真实 @标记指向目标机器人。问题正文只包含本次分析问题，不公开可选 `context`、咨询票据、完整会话历史或内部提示；因此 `question` 应写成适合在本群公开、能说明咨询目的的问题。

咨询 Hermes 前会先检查本机服务。应用会按需启动独立的 Hermes 对话服务；安装缺失、不可连接或检查超时时，本次不发布群提问、不提交模型任务，发起方会收到检查机器人连接状态的提示。关闭 Hermes 桌面不会停止此服务；退出本应用会清理自己启动的服务，既有配置和会话保留。服务异常退出后会重新启动，已提交的任务不会自动重发。显式配置了本机服务地址时，仍由该服务的所有者管理启动和退出。飞书机器人在线与 Hermes 本机执行端可用是两个独立状态。

随后桥接以目标机器人的身份，在同群展示它的最终答案；开启“在飞书显示处理进度”时也展示真实中途说明。中途说明只取执行端实际产生的 commentary，不展示内部推理或工具日志，也不按耗时编造进度；没有中途说明时直接展示最终答案。目标只需正常回答，双方模型都不额外调用发送工具或登记完成通知，也不在普通回复中重复发布同一咨询问题。

真实 @用于在群内展示咨询对象，咨询仍由现有 MCP 和桥接内部派发，不依赖机器人收到这条群消息后再次触发。机器人发出的咨询问题和答案不会作为新的用户指令形成循环；无需新增消息接收器或轮询群消息。

同一份分析结果通过本次 MCP 调用同步返回 `{target, answer, truncated?, groupReply?}`，源机器人在同一原生轮次继续处理，给出自己的判断与综合结论，不重复转发目标的完整答案；`truncated` 为真表示返回的答案被截断。目标保留自己的角色，使用独立的专用咨询会话分析所给问题，不合并双方完整历史，也不接续或改绑目标普通群会话。咨询会话按群聊、来源会话和目标机器人会话分别保存：同一来源会话再次咨询时可以理解“刚才的结果”等指代，包括跨轮咨询；任一方 `/new` 后使用新的咨询会话，切回旧会话则恢复原来的咨询历史。咨询意见不是新的操作授权；实际修改文件、执行操作或将工作交给对方继续时，使用现有交接流程。

分析结果返回与群消息送达是两个状态。`groupReply: "sent"` 表示目标最终答案已确认发到群内，`"uncertain"` 表示送达未确认。送达未确认时源机器人仍可使用答案继续分析，但须说明群内送达未确认，不能声称已发布，也不改用其他接口补发。此字段可选，兼容旧版返回；缺少字段不能作为群内发布成功的依据。

公开提问前必须能确认目标的真实 @身份。身份不可用时不会发布问题或启动目标；问题发送失败或送达未确认时也不会启动目标咨询，并向来源返回明确错误。来源机器人如实说明结果，不盲目重试或补发问题。

咨询用途通过模型指令约束，桥接会拒绝咨询中的审批请求；它不是操作系统层的只读沙箱，也不会修改 Hermes 的全局工具配置。

- 双方机器人、当前操作者及群必须通过桥接授权核验。私聊、本地预览和桌面续聊没有当前群咨询票据；普通提及、引用示例和讨论工具也不会发起咨询。
- 每个源轮最多顺序咨询 3 次，同一源轮只能有一个未完成请求。咨询目标不能继续咨询或交接，避免递归和互相等待。
- 模型答复等待上限为 45 秒，取得答复后最多再等待 8 秒确认群消息送达，MCP 客户端等待上限为 55 秒。仅群消息发送超时时仍返回已取得的答案，并标记送达未确认。缺少工具、票据失效、授权拒绝、超时或返回不明时应告知实际情况，不反复重试，不用文字交接或其他接口补发咨询。
- 需要停止时，向发起咨询的机器人发送 `/stop`，停止发起方任务及其正在等待的咨询。目标的专用咨询不使用它在群里绑定的普通会话。
- 继续复用当前桥接，不增加飞书接收器，也不通过额外群消息轮询答案。

本地验收时，分别覆盖 Codex 和 Hermes 作为发起方与目标方，确认同群按“来源公开提问并真实 @目标 → 目标公开回答 → 来源继续处理”的顺序展示；连续咨询时按“问题 → 答案 → 下一问题 → 下一答案 → 来源结论”展示。提问只包含 `question`，不泄露 `context`、票据或内部提示。开启进度显示时，目标真实中途说明和答案应以目标机器人身份出现；MCP 返回结果后源机器人继续同一原生轮次并给出综合结论，目标群会话绑定保持不变。没有真实中途说明或关闭进度显示时不应出现进度卡，公开问题与最终答案仍应展示。还需覆盖真实 @身份不可用、问题发送失败或送达未确认，确认不会启动目标；覆盖答案发送失败、停止与超时，确认如实报告状态且不伪称成功。无票据入口、历史票据、并行请求、超次和递归咨询应被拒绝或终止，不触发交接或模型额外补发；机器人群消息事件也不能重复派发咨询。
